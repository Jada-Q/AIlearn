# uu-80 — 护栏只会长在"会当场报错"的地方，不会长在重要的地方

> 这条挖自一场很平常的会话：读了一篇讲 AI 编程流程的文章，去补自己工具链上一个断掉的环节。补到一半发现，真正的洞不在那条链上——而是**我给自己装的所有防错机制，全都装在"已经动手之后"**。同一场结尾，又当场撞见一个活了不知道多久的静默 bug，正好是同一个机制的实锤。

---

## UU 1：不疼的错误，永远长不出护栏

### 实锤

扫自己 `~/.claude/hooks/` 下 20 个自动检查脚本，按它们**开火的时刻**排一遍：

```
想清楚之前   0 个
补细节之前   0 个
拆任务之前   0 个
写代码时     2 个   （前端 class 检查 / bash 中文变量检查）
跑命令时     3 个   （危险命令闸 / 影响范围声明 / 远程确认）
push/部署前  4 个   （三项核对 / 目录切换 / 部署红队 / 发布前陌生人视角）
宣告完成时   3 个   （要证据 / 验证层同层 / 验证器自身要能抓错）
```

唯一在前段开火的那个，管的是"要不要做这件事"，不管"想清楚了没"。

### 机制

**恶劣学习环境（wicked learning environment）** —— Robin Hogarth 提出的既有概念：一个环境是否适合从经验中学习，取决于**反馈是否及时、准确、可归因**。反馈良好的叫 kind，反馈延迟/缺失/误导的叫 wicked。

下游全是 kind 环境：部署挂了、验收假绿、push 漏文件——**当场报错，痛感即时，而且能准确归因到"我刚才那一步做错了"**。疼一次，就装一个护栏。

上游全是 wicked 环境：想歪了照样能跑通，代码没问题、页面打得开、部署也成功。**两天后才发现做的是不该做的东西，而那时归因会落到"这个 idea 不行"，不会落到"我当时没停下来问自己"。**

所以护栏不是按"重要性"生长的，是按"痛感的可归因性"生长的。这解释了一个反常识的现象：**一个人越是认真复盘、越是把每次翻车都固化成规则，他的护栏分布就越偏向下游**——因为只有下游会给他清晰的翻车信号。

同一形状会出现在别处：分发做得不好也不疼（没人骂你，只是没人看见），所以分发也长期没长出系统。

### 修法

想知道系统哪里有洞，别问"哪里重要"，问：**哪类错误不疼？**

但在不疼的地方装护栏，有两条硬约束，否则弊大于利：

1. **必须有死判据**（可以 `stat` 、可以 `grep` 的确定性条件）。上游的"你想清楚了没"是判断题，做成通用拦截 = 每次动手都弹提醒 = 几天后开始无视 = **连坐让现有的所有提醒一起脱敏**。拿一个没验过的新提醒去赌几个已经在起作用的旧提醒，这笔账不划算。
2. **第一版只提醒不阻断，而且自带记账**。升级成硬拦的决定权交给日志数字，不交给直觉。

实际落地的版本：只在"项目根目录还不存在"时开火——周级频率、可 stat 的死判据、代价最大的场景（做错了是浪费两天，不是浪费两分钟）。已有项目里"加第 N 个功能"这一类明知没覆盖，等日志数据出来再决定扩不扩。

## UU 2：全绿的输出，掩盖了 9 个从未备份的文件

### 实锤

同一场会话的收尾环节，自动备份管线里有这么一行：

```bash
git add CLAUDE.md ... commands/ rules/ skills/ ... 2>/dev/null
```

`rules/` 这个目录一个多月前就不存在了。`git add` 遇到不存在的路径会 `fatal` 并**中止整条命令**——一个文件都没加进去。而 `2>/dev/null` 把这条错误吞了。

后面每一环都真的成功了：
- 检查"有没有东西要提交" → 已跟踪文件的改动还在 → 判定有 → 继续
- commit 成功、push 成功、输出 `status: pushed` + commit 号

追回时才发现漏的不止这次：两个新工具文件，加上**此前几场会话遗留的 5 个笔记文件**，从未进过远端仓库。全都是我以为"已经存好了"的东西。

### 机制

**代理化（surrogation）** —— 管理会计里的既有概念：**用一个便于测量的代理指标替代真正关心的目标，久了就把指标当成目标本身**。

这里真正关心的是"所有该备份的文件都进仓库了"；代理指标是"有东西被暂存 + push 成功"。指标绿了，目标没成立。

更值得记的是：**这个 bug 能活这么久，正是因为它不疼**——备份漏了不报错、不影响任何日常操作，只在"哪天真丢文件想恢复"时才暴露，而那一天可能永远不来。

所以 UU 2 是 UU 1 的实锤，而且更狠一层：**连专门用来做收尾核对的那个管线本身，都长在了不疼的地方。检查器自己没有检查器。**

### 修法

**凡是「批量操作 + 吞掉错误输出 + 用聚合状态判成功」三件套同时出现，必然静默漏数据。** 改成逐项判定，或者至少让错误可见。

## 最高杠杆 1 条

不是"多写点文档"，是换一个提问方式：

> **本季度，哪类判断我做错了但没有任何东西报错？**

那里就是下一个该装东西的位置。

**立即可做的检查动作**（一条命令）：

```bash
grep -rn "2>/dev/null" <你的脚本目录> | grep -E "git add|cp |mv |rsync|for .* in"
```

命中的每一处，问一句：**这条如果部分失败了，我看得见吗？**

## 诚实反束

- 「护栏全在下游」是对**开火时机**的静态统计，不等于上游真的出过等量事故——那需要翻错误日志做归因统计，本场没做。
- 「恶劣学习环境」和「代理化」都是既有的公开概念，我用它们解释现象；但"这两个机制就是本例的成因"是我的推断，不是实验结论。
- 修复本身也没被独立验证：我用"仓库状态干净"判断修好了——**这又是一个聚合指标**。真正的验证应该是随机挑一个文件确认它在远端可读。这一步没做。
- 最讽刺的一点：UU 2 那个 bug 不是任何机制抓出来的，是我在同一场会话里第二次跑收尾流程时顺手看了眼提交内容才撞见的。**如果没跑第二次，今天它还在漏。**
- 分析者本身是没被验证的验证器。同一场会话里，我自己还犯了一次"改完没复跑检查就宣告为零"。
