# 拆开 agent 的身体：读 DeepSeek Harness 源码搞懂我天天在用的东西

> 2026-08-14 · DeepSeek Harness 开源次日，clone 下来读 agent loop 源码的三层收获

2026 年 8 月 13 日，DeepSeek 把自家的 agent harness（`deepseek-harness`，MIT 协议）开源了，定位是 Claude Code 的开源同类。我每天在 Claude Code 里工作，但它对我一直是黑盒——这是第一次有一个结构类似的产品把完整实现摆出来。我把它 clone 下来，读了核心的 agent loop 部分（`packages/core/agent-loop/`，一共 1643 行）。以下是三层收获。

---

## 一、"智能循环"其实只有一行

先说最大的祛魅。整个 agent 的心脏，在 `agent.ts` 里就是：

```ts
while (await this.turn()) {}
```

一行 while。展开成流水线，每一步（step）干的事是：

1. 用户输入进"收件箱"（inbox）
2. 组装一封信：系统提示词 + 工具清单 + **从头到现在的全部历史**
3. 寄给模型，流式收回信
4. 检查回信里有没有"工具调用"块
5. 没有 → 这轮结束；有 → 真的去执行工具（读文件 / 跑命令），把结果记进历史，回到第 2 步

两个关键认知：

**模型是彻底失忆的。** 每一步都把全部历史重新寄一遍。所谓"agent 有记忆、在连续思考"是幻觉——真相是快递员每次都把整本聊天记录复印一份塞进信封。"智能"全在远端模型，harness 只是**记账员 + 跑腿**。

**agent loop 是圈，不是直线。** 我原来把它理解成"文字 → 模型 → 工具 → 修好"的单程流水线。实际上工具跑完的结果不是终点，而是下一圈的输入：结果入账 → 整本账重新寄给模型 → 模型看着结果再决定动不动 → 直到某一圈回信里不再有工具调用。改一个 bug 通常转好几圈：读文件、改文件、跑测试、测试挂了再改。工具只是手，修复的判断始终在模型。

## 二、账本原则：为什么这样搭 + 哪里必崩

`agent.ts` 第一行注释就写着设计核心："Every request is derived from the session log"——一切从会话日志派生。内存状态断电就没了，日志写盘就能恢复，所以 Claude Code 崩了能 resume，原理就是重放日志。这个 repo 的铁律叫 **"Model-visible ⟺ logged"**：凡是模型能看到的，必须能从日志重建。类比：公司不靠老会计的脑子记账，靠账本，换人也能接。

从这个结构能直接推出三个**必然**崩溃点（不是 bug，是物理）：

1. **当每步都重发全部历史时，上下文塞爆必然发生，因为历史只增不减。** 所以必须有压缩（compaction）插件在旁边盯着。你在 Claude Code 里看到的 context 条、自动 compact——不是产品功能，是这类机器的结构性必然，每家都得做。
2. **当依赖网络流式传输 + 模型概率性输出时，单次请求失败必然发生。** 所以 loop 里专门留了 request-error 事件口，配 retry 插件在外面接住。你见过的 "API error, retrying..." 就是这层。
3. **循环本身没有刹车。** repo 的「已知限制」原话：没有内置轮次预算——只要模型不停地要调工具，轮次就一直跑。agent"跑飞"是结构性风险，刹车必须外挂。

账本原则还回答了一个我答错的问题：**agent 干活到一半按 Esc，刚发出去还没返回的命令会怎样？** 我猜"跑完但结果被扔掉"。错——真实行为是：中止只阻止**启动新的**调用，**已启动**的调用会等它收尾，**并把结果记入账本**。为什么？因为那条命令对世界的影响是真实发生的（进程跑了、文件可能改了），把结果扔掉，账本就在撒谎——下次恢复会话时模型的认知和现实脱节，后面全错。甚至没来得及发出的调用，也会补一条"取消"标记进账本，宁可记"这条被取消了"也不留空洞。

一句话：**Esc 掐的是"下一步"，不是"已发生的事实"；事实只能入账，不能撕页。**

## 三、边界：harness 定下限，模型定上限

**能**：核心循环刻意做得极小，模型只是配置里的两个字符串（`{provider, model}`）——所以"换大脑"天然容易，模型无关不是营销词，是架构副产品。repo 自己的规矩是 "Plugins, not loop changes"：循环冻结，一切新行为走插件。

**不能**：loop 完全不懂内容。它不判断模型说得对不对、危不危险，只机械执行"有 tool call 就跑"。权限弹窗、沙箱、计划模式全是外挂插件。推论：**harness 决定下限（不崩、可恢复、可取消），模型决定上限（聪不聪明）。换一个更好的 harness 不会让 agent 变聪明，只会让它死得少。**

这层还从架构上解释了我踩过的一个坑：为什么写在 CLAUDE.md 里的规则会"临场不激活"，改成 hook 就稳了。从 loop 视角看，CLAUDE.md 只是信封里"系统提示词"那段**文本**——每步重发、模型概率性遵守；而 hook 是挂在工具执行前后的**确定性代码**——条件命中必然执行。文本层管不住的，代码层管。这不是某家产品的怪癖，是这类机器的物理结构。
