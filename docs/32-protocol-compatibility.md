# 协议决定你哪些东西能一天换掉，哪些一换就重做

> 2026-08-12 · 一次没采用的工具试用，照出了我自己项目里做对却说不出名字的事

## 一个失败的下午

我看到一篇文章介绍三个语音 AI 开源项目，其中一个叫 qwen-audio-agent，定位是「实时语音运行时」：你对着电脑说话，前台一个小模型陪你聊，判断这活该交出去的时候，把任务派给后台的编程 agent（Claude Code / Codex / Kimi Code 都能接）。后台干活期间对话不中断，你还能问进度、喊停。

我装了。全本地跑：语音识别、对话模型、语音合成三个模型都在自己的 M4 Pro 上，一分钱云端费用不花。

装完实测，端到端从我说完最后一个字到听见第一个音，**1.11 秒**（三轮 1.10 / 1.11 / 1.12）。这个数字比我三个月前的估计好——当时我判断「本地三段式必然掉到 1.5–2.5 秒」，实际没那么慢。

然后它在最关键的一步崩了：**派活 0 次**。

我说「帮我查一下今天的 AI 新闻」，它没有交给后台，而是用那个 4B 小模型自己硬答——既慢又答不出（本地模型不能上网）。查 gateway 日志，派活相关事件数是 0。

根因不在提示词，在机制：本地模型这条路**没有原生的工具调用**。它的实现是把工具说明塞进系统提示词，要求模型在回答里吐出格式精确的 `<code>...</code>` 文本块，再用正则表达式把它抠出来。一个 4B 模型要读完 156 行中文规则、判断该派活、还要吐出格式完全正确的代码块——做不到。

于是我不采用。坐在电脑前的时候，macOS 自带听写把话变成文字丢进 Claude Code，更准更快、零安装；而它想解决的「人离开电脑后只剩漫长安静」那个痛，我坐在终端前盯着输出，本来就不存在。

**但这个下午不算白费。因为在解释它为什么值得一试的时候，我说了这么一句：**

> 它的语音层兼容 OpenAI Realtime 协议，所以云端和本地能一行配置互换。

说完我才反应过来：这件事我自己的项目里早就在做，只是我一直没给它起过名字。

## 它照出了我自己项目里的三层

我有个项目叫 tokyo-strata，把东京 22 区 290 万栋建筑做成可交互的形态地层图，数据是一个 50 MB 的 PMTiles 文件。它里面叠了三层协议兼容，我逐层拆给你看。

### 第一层：HTTP Range —— 我被它咬过一次

先看一个实验。这是我的线上站现在正在做的事：

```
$ curl -sI -H "Range: bytes=0-127" https://tokyo-strata.vercel.app/data/tokyo.pmtiles
HTTP/2 206
accept-ranges: bytes
content-range: bytes 0-127/50421593
content-length: 128

$ curl -sI https://tokyo-strata.vercel.app/data/tokyo.pmtiles
HTTP/2 200
content-length: 50421593
```

同一个文件、同一个地址，**问法不同，给的东西不同**。第一次我说「只给我第 0 到 127 个字节」，它回 206（部分内容）加 128 字节；第二次不加条件，它回 200 和完整的 50 MB。

这套「怎么问、怎么答」的规矩，就是协议。

为什么重要：那个 PMTiles 有 50 MB。如果每个访客打开网页都要先下 50 MB，没人等得起。所以浏览器里的客户端是这么干的——先只要开头几百字节（那里是目录，写着哪块楼在文件的哪个位置），读完目录再精确地说「把第 3,240,000 到 3,290,000 字节给我」，那正好是用户当前看的几个街区。

**访客永远只下载他看得见的那部分。** 50 MB 的文件，实际可能只传了 200 KB。

而我踩过的坑正在这里。本地测试时我用 `python3 -m http.server`，地图上一栋楼都不出，控制台报错。折腾了半小时才发现：

| 服务器 | 会不会说 Range | 结果 |
|---|---|---|
| `python3 -m http.server` | 不会。你问它要 128 字节，它回你整个 50 MB 加 200 | 客户端发现「我要 128 你给我 5000 万」→ 报错 |
| `npx serve` / Vercel / nginx | 会，回 206 | 正常 |

代码一个字都没错，只是选了个不说标准话的服务器。

**这是协议兼容最赤裸的样子**：前端代码完全没动，换个服务器，从崩到通。

它给我的实际自由是：这份数据现在挂在 Vercel，哪天想换 Cloudflare、换自建 nginx、换 GitHub Pages，`index.html` 一行都不用改。我不是被 Vercel 绑住了，我只是被「会说 HTTP Range 的服务器」这个集合绑住了——而那个集合几乎是全部。python http.server 是集合外面的少数派。

### 第二层：addProtocol —— 字面意义上的适配器

我的代码里有这么三行：

```js
const pmtilesProtocol = new pmtiles.Protocol();
maplibregl.addProtocol('pmtiles', pmtilesProtocol.tile);
map.addSource('bldg', { type: 'vector', url: 'pmtiles://./data/tokyo.pmtiles' });
```

第二行那个函数就叫 `addProtocol`——「加一个协议」。这不是巧合。

发生了什么：画地图的库（MapLibre）**不认识 PMTiles 这个格式**。它只认识一种数据源——「给我第 z 层第 x 行第 y 列那一块瓦片」。而 PMTiles 是把整个瓦片金字塔塞进单个文件的格式，MapLibre 完全不懂。

于是中间垫了个翻译器。`addProtocol` 这句话是在跟 MapLibre 说：

> 以后你看到地址开头是 `pmtiles://` 的，别自己处理，交给这个函数。它会把你要的 z/x/y 翻译成对那个大文件的字节范围请求，取回来再变成你认识的瓦片交给你。

而 qwen-audio-agent 里有个一模一样的东西。它的 gateway 只会说一种协议（Zed 定义的 Agent Client Protocol，简称 ACP），OpenCode、Kimi Code 这些天生就会说，直接接上；**Claude Code 不会说 ACP**，所以中间垫了个叫 `claude-code-acp` 的翻译器。

两边是同一个角色：

| | tokyo-strata | qwen-audio-agent |
|---|---|---|
| 主程序只会说一种话 | MapLibre 只认 z/x/y 瓦片 | gateway 只会说 ACP |
| 对方不会说那种话 | PMTiles 是单文件格式 | Claude Code 不说 ACP |
| 中间垫翻译器 | `pmtiles.Protocol()` | `claude-code-acp` |
| 结果 | MapLibre 以为自己在正常取瓦片 | gateway 以为自己在跟标准 ACP agent 说话 |

**两边都不知道中间有人在翻译，这就是适配器做得好的标志。**

### 第三层：通用数据格式 —— 换渲染库的自由

再往上一层。那个 `.pmtiles` 里装的是标准矢量瓦片（用 tippecanoe 生成的），不是某个库的私有格式。

意思是：哪天我不想用 MapLibre 了，想换 deck.gl、换 Mapbox GL、换别的——**290 万栋楼那份数据一个字节都不用重新生成**。数据是我的资产，不是某个库的附属品。

反过来，如果当初存成了某个库私有的格式，换库就等于重跑整条数据管线。

## 三问

把上面这些收成一个可以随身带的东西。**开新项目、或者引入一个新的平台 / SDK / 托管服务之前，问自己三句话：**

**1. 我这东西对外说的是标准话，还是某一家的方言？**

标准话 = HTTP、OpenAI 兼容接口、通用文件格式。方言 = 某平台的私有 SDK、私有数据格式。

**2. 我的核心资产，能不能脱离当前工具活下来？**

把数据和产物拷到别处，它还是不是有效的？如果只能在某个云平台的数据库里存在，危险。

**3. 我依赖的那个东西，有没有「同协议的本地或开源替代」？**

有 → 你可以先用贵但稳的跑通，之后随时换省钱的。没有 → 你在给自己上锁，得想清楚值不值。

这三问的作用**不是否决，是划线**。

## 可换 / 不可换那条线

拿 tokyo-strata 盘一遍就清楚了：

| 想换的东西 | 能不能换 | 为什么 |
|---|---|---|
| Vercel → Cloudflare / 自建 nginx | ✅ 改个 DNS，代码不动 | 大家都说 HTTP Range |
| MapLibre → 别的地图库 | ✅ 数据不用重做 | 矢量瓦片是通用格式 |
| PMTiles → 别的瓦片方案 | ⚠️ 要换适配器，但数据可转 | 换翻译器，不换数据 |
| 那 290 万栋楼的数据本身 | ❌ 重做要重跑整条管线 | 这是真资产，也该是最难换的 |

**规律是**：越靠外层（服务器、渲染库）越应该能随便换；越靠核心（你的数据、你的分析）越不该换也换不了。

**协议的作用，就是把「可换的」和「不可换的」之间划一道清晰的线。**

这条线画对了，换任何外围工具都是一天的事。画错了——比如把核心数据存成某个工具的私有格式——换个工具等于重做项目。

而这也正是那个语音项目唯一真正值钱的设计：因为它的语音层兼容 OpenAI Realtime 协议，「用阿里云」和「用我自己电脑」之间的差别只是配置文件里两行字。这个能力的实际意义是——

> 先用贵但稳的云端 API 把产品做出来，跑通了、验证了，再悄悄换成本地。用户不知道，你的代码也不用改。

**你不需要在「省钱」和「能跑」之间提前赌一把。**

## 附：这次学到的另外三个技术判断

顺手记下，都是这次实测得到的，不是从文档抄的。

**1. 「反应慢」经常是「它在自己硬答」的表象。** 我差点去调语音合成的参数，方向全错。先查有没有真的调用工具（看日志里的派活事件数），再谈优化延迟。

**2. 看到「本地小模型 + 工具调用」的方案，先查它是原生 function calling 还是文本块正则解析。** 后者加小模型 = 一定不稳，跟提示词写得好不好无关。推论：「本地跑省钱又隐私」这个直觉在**纯生成**任务上成立（识别、合成、翻译、摘要），在**需要可靠工具调用的调度**任务上不成立。要分开评估。

**3. Apple Silicon 上多模型流水线的延迟是累加的，不是取最大值。** 源码里有个全局锁，注释写着：MLX 模型在 Metal 上不能被多线程并发使用。所以语音识别、对话、合成三个模型必须排队用 GPU。这是物理约束，改代码绕不开——1.11 秒就是三段串行相加的结果。评估任何 Apple Silicon 上的多模型系统，都要先问这个问题。
