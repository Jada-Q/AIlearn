# 计划的第一步就是编的：多 agent 评审里，"现有资产"必须实查

> 2026-09-13 · 来自一场 14-agent 候选评审（7 个计划 agent + 7 个红队 agent）的实战翻车与拦截

## 场景

我用多 agent workflow 评审 7 个产品候选：每个候选一个"计划 agent"（联网调研 + 写出先探针后建造的计划），再各配一个"红队 agent"（独立复核承重事实 + 尽全力杀死这份计划）。

其中一个候选是"把手上的 AI 动画连续剧项目重构成竖屏短剧供片"。计划 agent 写出的探针第一步是：

> "用项目现有素材剪一版 60-90 秒竖屏样片，只用已生成素材不新烧生成额度——预计 3 小时。"

听起来无懈可击：低成本、复用现有资产、不写代码。

## 翻车点

红队 agent 跑了一条 `find`：**那个项目目录里有 0 个视频、0 张图像**——只有 6 个 markdown 规划文档。而且项目文档里明写着"视觉风格定案：方案已毙，待对比测试"、"分镜剧本待重做"。

也就是说，探针的第一步引用的资产**根本不存在**。真实探针成本不是"3 小时剪辑"，而是从零生成一部平台级样片——比纸面高一个数量级。如果照计划动手，"低成本探针"会在第一步就静默膨胀成一次完整建造。

## 为什么会发生

计划 agent 读了项目的规划文档（PRODUCTION.md、分镜脚本），从"文档里详细描述了 6 集内容"推断出"素材已存在"。这是一个非常典型的 LLM 失效模式：

**规划文档描述的是意图，不是库存。** LLM 分不清"计划里的资产"和"仓库里的资产"——两者在文本上长得一模一样。

而且这个错误有伪装性：计划的其余部分（市场调研、条款问题清单、GO 门槛设计）全部质量在线、来源可查。**一份 95% 严谨的计划，最容易让那 5% 的编造混过去。**

## 三条可操作教训

1. **计划里引用本地资产 → 先 `ls` 盘点。** 任何"用现有的 X 做 Y"，在写进计划前必须有一条实际执行过的 `ls` / `find` / 文件读取作为证据。探针原料要清单化，不能从描述性文档推断。
2. **agent 自报不作数，对抗复核必须"独立执行"而非"转述检查"。** 红队 agent 的 prompt 里明确写了"挑 2-3 个决定生死的承重事实，自己动手复核，计划作者的话不作数"——它才会真的去跑 `find`，而不是复读计划的声明。
3. **主循环对"决定判决的事实"再亲验一遍。** 红队也是 agent，红队的话同样不作数。这个案例里，主循环最后自己又跑了一次 `find` 确认 0 个媒体文件，才把判决写进交付物。三层里任何一层偷懒，编造就会存活。

## 为什么这个坑值得单独记

它是"探针门槛被纸面低估 → 动手后变成建造"这个经典死法的 AI 版本。人类创业者高估自己资产的方式是乐观记忆；AI 计划体高估资产的方式是**把文档当仓库**。防御方式恰好相同：动手前对着仓库点货，而不是对着计划书点头。
